# ADR 0004: 通知的检测与送达机制

**状态**:已接受

通知按性质拆成**两轨**,检测方式不同:

- **轨 1 收件箱(存储)**:用户操作触发的真·离散事件,本期仅 `assigned`(分配/改派)。业务代码同步写 AppNotification(targetUserId = 新责任人),有已读/未读 + toast,无定时任务。
- **轨 2 我的待办(读时计算,不落库)**:overdue / due_soon / 待首响 / 检查点未达 / 特急欠跟进等时间类告警,本质是随 `now` 持续变化的**派生条件**而非离散事件。查询当前用户(assigneeId = me)名下工单、套用时间谓词,即得"我此刻的待办",红点计数呈现。

送达:前端 **30 秒轮询**,一次请求合并两轨。当前量级(50+ 并发)下轮询足够,SSE/WebSocket 不必要。

拒绝的方案:cron 扫描生成通知行 + 去重表——与 ADR 0001"读时算"自相矛盾(同一个 dueAt 判断算两遍),且派生一串并发症:改派后接收人冻结在旧责任人、改等级要考虑补发错过的检查点、滚动提醒要计数去重。读时计算天然消灭这三类问题:按当前 assigneeId 算、只算现在、条件为真即显示消解即掉出(天然幂等)。

边界:

- comment、status_change、新单入库**不进任何轨**(无合理接收人,或已被 assigned 通知覆盖;未分配池靠看板,主管主动处理)
- 未分配工单(assigneeId = null)不进任何人的待办
- 待办谓词与看板"已超时数 / 2小时预警数"**必须共用同一判定函数/视图**(呼应 ADR 0001)
- 二期带外推送(邮件/飞书)时才引入后台定时任务,专供带外通道的检测与去重(带外是真·离散投递);站内轨 2 仍读时计算不变
