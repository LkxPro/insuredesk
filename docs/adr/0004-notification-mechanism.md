# ADR 0004: 通知的检测与送达机制

## 状态

已接受

## 上下文

系统需要向用户推送通知（AppNotification）。经逐类审视，通知类型收敛为 **3 种**：`assigned`（被分配/改派）、`overdue`（已超时）、`due_soon`（快超时）。设计时发现"实时通知"其实是两个正交的问题，必须分开决策：

1. **检测**：谁来发现"一个需要通知的事件发生了"？（时机 / 计算）
2. **送达**：发现之后，怎么让用户的浏览器看到？（传输通道）

> 注：初版曾设计 6 种通知类型，后砍掉 `comment`（跟进，无合理接收人）、`status_change`（状态变更，操作人自己触发或已被 assigned 覆盖）、`new_ticket`（新单入库无接收人，主管靠看板处理）。first-assign 与 reassign 合并为 `assigned`。

### 检测：通知分两类，命运不同

- **用户操作触发类**（assigned）：是某个用户点了按钮的副作用（分配 / 改派）。处理该操作的后端代码顺手写一条 AppNotification 即可，**无需任何定时任务**。
- **时间流逝触发类**（overdue / due_soon，以及 §4.2 的首响提醒、跟进频次提醒）：没有任何人点按钮，事件因"时间到了"而发生。**必须有后台定时任务定期扫描**（查 dueAt 将到/已过且未完结的工单），否则无人能在超时时刻主动生成通知。

关键认知：这与 ADR 0001 不冲突。ADR 0001 的"无定时任务"仅指显示状态实时计算；而"用户没打开页面时也要收到超时通知"是 ADR 0001 未覆盖的盲区，必须靠定时任务补上。传输层再实时（哪怕 WebSocket）也不能自己发现"工单超时了"——检测这一步绕不开。

### 送达：三种传输方案

- **轮询（Polling）**：前端每 N 秒查一次"我有未读通知吗"。实现最简单（一个 GET 接口 + 前端定时器），延迟 = 轮询间隔。
- **SSE（Server-Sent Events）**：服务器→浏览器单向长连接，真·实时。复杂度在连接管理（多标签页、断线重连、多实例部署时定位连接）。
- **WebSocket**：全双工，对纯接收通知的场景是杀鸡用牛刀（用不到浏览器→服务器方向）。

## 决策

**检测**：
- 用户操作触发类通知：在处理该操作的业务逻辑中**同步写入** AppNotification，无定时任务。
- 时间流逝触发类通知：由一个**轻量后台定时任务**周期性扫描生成，覆盖两部分：
  - **超时 / 快超时**（overdue / due_soon）：扫描 dueAt，与数据看板"已超时数 / 2小时预警数"复用同一时间判断条件。
  - **SLA 提醒引擎**（首响提醒、跟进检查点、滚动提醒）：按 SLAPolicy 的三种 ReminderRule 类型评估（见 ADR 0005、PRD §3.8）。
- 所有时间流逝类判定的时钟起点为工单 **createdAt**（滚动提醒以上一条 comment 为基准）。

**送达**：采用**轮询，间隔 30 秒**。前端每 30 秒查询当前用户的未读通知（`AppNotification WHERE targetUserId = 当前用户 AND read = false`），亮红点 / 弹 toast。

## 理由

1. **量级匹配**：PRD 目标为 50+ 并发用户、列表加载 <1 秒。30 秒轮询一个轻量查询，后端压力可忽略。
2. **足够的实时性**：被分配 / 超时 这类事件，晚 30 秒知晓不影响业务（非抢单式硬实时）。
3. **不搞庞大架构**：轮询就是普通 GET 接口 + 前端 setInterval，无长连接、无连接管理、无新组件，契合"简单工单系统"的定位。
4. **升级路径无痛**：轮询与 SSE 对前端是同一套 UI（拿通知列表 → 亮红点 → 弹 toast），仅数据来源层不同。未来若需秒级体验，只替换送达层为 SSE，前端通知组件与检测层均不动。今天用轮询不构成技术债。

## 影响

- 需要引入一个后台定时任务（如 node-cron / 数据库定时器 / 云函数触发器），仅用于生成"时间流逝触发类"通知。这是对 ADR 0001"无定时任务"表述的范围修正：显示状态仍实时算，通知生成需定时扫描。
- 定时任务的扫描周期需与"送达轮询 30 秒"量级匹配（建议 1~5 分钟扫一次），避免通知生成延迟远大于送达延迟。
- 前端需实现一个全局轮询器（30 秒），统一拉取未读通知并驱动红点 / toast。
- 时间流逝类通知的**去重规则（一单一类型一次）**：同一工单 + 同一通知类型（overdue / due_soon）在全生命周期**只生成一次**。定时任务需持久化"该工单该类型已发"标记，后续扫描到即跳过，避免每次扫描重复刷屏。用户即便漏看通知，看板的实时红色标记会持续呈现，形成兜底。
- overdue / due_soon / SLA提醒 的接收人为工单**当前 assigneeId**；工单**未分配时（assigneeId=null）不发送任何提醒通知**——超时/预警靠数据看板呈现，主管主动处理未分配池。
