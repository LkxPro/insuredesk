# ADR 0004: 通知的检测与送达机制

## 状态

已接受

## 上下文

系统需要向用户推送提醒。经逐类审视，提醒收敛为两大族：`assigned`（被分配/改派，**用户操作触发**）与一组**时间流逝触发**的告警（`overdue` 已超时、`due_soon` 快超时、待首响、跟进检查点未达、特急欠跟进）。设计时发现"实时通知"其实是两个正交的问题，必须分开决策：

1. **检测**：谁来发现"一个需要提醒的条件成立了"？（时机 / 计算）
2. **送达**：发现之后，怎么让用户的浏览器看到？（传输通道）

> 注：初版曾设计 6 种通知类型，后砍掉 `comment`（跟进，无合理接收人）、`status_change`（状态变更，操作人自己触发或已被 assigned 覆盖）、`new_ticket`（新单入库无接收人，主管靠看板处理）。first-assign 与 reassign 合并为 `assigned`。

### 关键转折：时间类告警是"派生条件"，不是"离散事件"

初版把时间类告警当成"事件"——由后台定时任务扫描 dueAt/SLA 规则**生成通知行并存库**，再配一套"一单一类型只发一次"的去重标记。复盘发现这与 ADR 0001 的既有结论**自相矛盾**：ADR 0001 已确立"overdue / pending_timeout 是随 `now` 持续变化的**显示状态**，读时计算、不落库、无需定时任务"。而通知侧却要为**同一个 dueAt 判断**再建一套"扫描 + 生成 + 去重"的机制，把同一件事算两遍。

更进一步，`overdue`/`due_soon`/"待首响"/"检查点未达"/"特急欠跟进"本质都是**当前是否满足某谓词**（`now > dueAt`、`now - lastCommentAt ≥ 12h` 等），条件为真则该工单**此刻**需要关注，条件消解（跟进/完结）即不再需要。这类"持续条件"用"离散事件 + 去重"建模会派生出一堆并发症：改派后接收人已冻结在旧责任人、改等级后错过的检查点要不要补发、滚动提醒的"第 N 次"如何计数去重。

### 检测：两类通知，命运不同

- **用户操作触发类**（assigned）：是某个用户点了按钮的副作用（分配 / 改派）。处理该操作的后端代码顺手写一条 AppNotification 即可，**无需任何定时任务**。这是真·离散事件，值得存储。
- **时间流逝触发类**（overdue / due_soon / 待首响 / 检查点 / 滚动）：是随时间持续变化的派生条件。**读时计算**即可——查询当前用户名下工单、套用时间谓词，就是"我此刻的待办告警"。无需生成、无需存储、无需去重。

### 送达：三种传输方案

- **轮询（Polling）**：前端每 N 秒查一次。实现最简单（GET 接口 + 前端定时器），延迟 = 轮询间隔。
- **SSE**：服务器→浏览器单向长连接，真·实时；复杂度在连接管理。
- **WebSocket**：全双工，对纯接收通知是杀鸡用牛刀。

## 决策

采用**两轨制**，检测方式随通知性质分开。

**轨 1 — 收件箱（用户操作触发，存储）**：
- 本期仅 `assigned`。在处理分配/改派的业务逻辑中**同步写入** AppNotification（targetUserId = 新责任人），无定时任务。
- 有已读/未读、来了弹 toast。这是真·离散事件，值得留痕。

**轨 2 — 我的待办（时间流逝触发，读时计算，不落库）**：
- `overdue` / `due_soon` / 待首响 / 跟进检查点未达 / 特急欠跟进等，**不写 AppNotification 表**。
- 由前端 30 秒轮询时，查询当前用户（assigneeId = me）名下工单，套用时间谓词（`dueAt`/`now`/`lastCommentAt`/comment 累计数）**实时计算**出"我此刻的待办告警清单"，以红点计数呈现。
- 判定谓词见 PRD §3.8 / §4.2，与数据看板"已超时数 / 2小时预警数"**复用同一时间判断条件**（收敛到单一函数/视图，杜绝口径漂移）。
- 时钟起点为工单 **createdAt**（滚动告警以上一条 comment 为基准）。

**送达**：采用**轮询，间隔 30 秒**。前端每 30 秒发一次请求，同时拉取轨 1 的未读 `assigned` 通知 + 计算轨 2 的待办告警，驱动红点 / toast。

## 理由

1. **消除"算两遍"**：时间类告警与看板复用同一读时判断，不再为同一个 dueAt 维护第二套"扫描+生成+去重"机制。与 ADR 0001"显示状态读时算"一脉相承。
2. **一次性消灭一整类并发症**（全是"生成-存储"模型的固有毛病）：
   - **接收人冻结**：若 overdue 通知在改派前已发给旧责任人 A，改派给 B 后 B 永远收不到。读时计算按**当前** assigneeId 算，改派后自动出现在 B 的待办、从 A 消失。
   - **改等级不补发**：读时只算"现在"，没有"补发历史检查点"这个动作，规则天然只对未来生效。
   - **去重表 / 滚动计数**：待办是"条件是否为真"，条件仍真就一直显示、消解即掉出，天然幂等，无需持久化"已发"标记。
3. **量级匹配**：50+ 并发、列表 <1 秒。30 秒轮询一句带 `assigneeId` 索引的过滤查询，后端压力可忽略；比"轮询通知表 + cron 全表扫 + 维护去重表"三件套总活儿更少。
4. **足够的实时性**：被分配 / 超时这类事件，晚 30 秒知晓不影响业务（非抢单式硬实时）。
5. **升级路径无痛**：轨 2 的读时查询未来正是"带外推送"的检测逻辑，不白写；前端通知 UI（红点/toast）在轮询→SSE 升级时也不动。

## 影响

- **本期无后台定时任务**：这是对初版"cron 扫描生成时间类通知"的推翻。显示状态与待办告警都读时算；`assigned` 同步写。
- **AppNotification 表瘦身**：`type` 本期仅 `assigned`；`overdue`/`due_soon` 等不再落库（见 PRD §3.7）。
- **前端需实现一个全局轮询器（30 秒）**：一次请求内合并"拉未读 assigned + 算待办告警"，统一驱动红点 / toast。
- **待办查询与看板统计必须共用同一判定函数/视图**：`overdue`（`now > dueAt` 且未完结）、`due_soon`（`dueAt - now < 2h` 且未完结）、待首响（无第一条 comment）、检查点、滚动——集中一处实现，前端染色、待办、看板卡三处复用。
- **升级到带外推送（二期）**：当需要"人不在应用内也收到邮件/飞书"时，再引入一个后台定时任务**专供带外通道的检测与去重**（那时才需要"已发"标记，因为带外推送是真·离散投递、不能重复发）。站内轨 2 仍走读时计算不变。
- 未分配工单（assigneeId=null）不进任何人的待办（查询带 assigneeId=me 天然排除），超时/预警靠数据看板呈现，主管主动处理未分配池。
