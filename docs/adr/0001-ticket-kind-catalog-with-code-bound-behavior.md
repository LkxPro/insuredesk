# 工单种类 = 目录数据 + 行为按 key 绑代码

支持投诉之外的工单种类（首个：退费异常）时，新增 `ticket_kinds` 目录表（key/name/active/sortOrder），工单存引用。种类元数据（名称/排序/启停）归管理员维护；种类**行为**（录入通道、详情页模块、完结回调、SLA 计时锚）按种类的稳定 key 类型化绑定代码，行为绑定的行只启停、不物理删除、key 不可改——key 是代码契约。SlaPolicy 随之按种类分组（组内排序契约、下拉种类过滤与服务端强制匹配、导入按名匹配限定投诉组、dashboard 特急卡限投诉组）。

## Considered Options

- **复用客诉类别字典**（业务文档原方案：类别=卡异常退费失败/其它异常退费失败）——类别是管理员可改名/停用的易变字典，行为绑定易变数据会脆断；且两个退费子类型会污染手工建单的类别下拉。workOrderType 最终降格为扩展数据里的纯展示文本，不进任何目录。
- **source 枚举加值**——source 是录入方式判别器（CONTEXT.md 明令勿与分类维度混用），且是纯硬编码枚举，与「种类可配」的诉求背道而驰。推送录入仍新增 source=`jb-insurance`，那是录入方式，与种类正交。
- **通用元模型**（管理员运行时自定义字段 schema/表单/回调模板）——违背仓库既定的反通用化立场（SLA 提醒规则只接受系统提供的类型化规则，不接受自定义表达式），工程量数倍，且外部合同（推送/回调报文）本来就是对端写死的，做成配置是假象灵活。

## Consequences

新增「同形状」种类（只换名字、无新行为）零代码，加目录行即可；携带新行为的种类仍需开发。种类目录进字典管理页第 6 张卡，key 列只读。
