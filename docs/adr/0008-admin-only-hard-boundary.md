# ADR 0008: 管理员是唯一硬边界,其余权限委托即全信任

**状态**:已接受

角色模型收敛为两类:**管理员**(唯一系统角色)与**普通角色**。"受保护预设"概念删除——出厂 seed 生成的客服主管/一线客服/只读观察只在系统首次初始化时建一次,之后与手建角色无任何区别(可改名/改权限/删除,删了不复活,无恢复出厂功能)。

管理员三项全锁(名称/权限/删除),其权限**不读库中配置,恒为当前代码的全量权限点**——版本升级新增权限点自动获得,永不需要同步迁移。管理员的领域语义是"不受权限配置约束的系统角色",而非"恰好勾了所有框的角色"。

系统唯一的硬性防护是一条不变量:**始终至少一个启用状态的管理员用户**——禁用用户或改派角色若使其归零则拒绝。除此之外零技术防护:`role.edit_permission` 与 `user.assign_role` 定义为管理员级信任的委托,授出即等于授出全部——前者可给任何非管理员角色(含持有者自己的)配置任意权限点,后者可把管理员角色派给任何人(含持有者自己)。威胁模型是**误操作而非内部攻击者**,误操作的最坏情况由不变量兜底。

拒绝的方案:

- **受保护的预设角色**(原状)——预设/自定义两套编辑规则,UI 两个分区,换来的只是"出厂配置不被改动",而出厂配置本就该被各家改成自己的样子。
- **启动时把管理员权限数组刷成全量**——"库里的值不可信、会被覆盖"的半真半假状态,不如根本不读。
- **子集规则**(只能授予自己持有的权限)——防不住合谋(A 改 B 的角色、B 再改 A 的),却误伤合法委托。
- **管理员角色仅管理员可授**——单点确实有效,但被有意否决:所有管理员级委托保持同一口径("授出即信任到顶"),不为其中一条单开例外。

影响:"持有 `user.assign_role` 的主管可自封管理员"**是有意设计,不是漏洞**——安全审查或未来读者请勿当 bug 修掉;授权者须知授出 `role.edit_permission` / `user.assign_role` 即等于授出整个系统。数据范围维持两档(全部/个人)不受本决策影响。存量部署迁移:`Role.preset` 改造为 `system`(仅管理员为 true),原三个预设角色翻为普通角色。
