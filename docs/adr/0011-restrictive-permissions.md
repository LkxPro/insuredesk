# ADR 0011: 限制类权限——勾选=禁止,管理员全量展开排除

**状态**:已接受(修订 ADR 0008 的"全量权限点"表述)

权限矩阵引入**限制类权限**:勾选=禁止对应操作,与正向权限(勾选=授予)语义相反。首个权限点 `user.forbid_change_own_password`(禁止修改自己的密码)。限制类权限与正向权限同用 `role.permissions` 一个数组存储和校验,语义差异只体现在权限点定义层的独立清单(`RESTRICTIVE_PERMISSIONS`)与消费端;权限点清单 UI 以独立分组展示并标注"勾选=禁止"。

管理员的动态全量展开(ADR 0008)收敛为**全量正向权限点**:限制类权限若进入展开,管理员将被自动禁止对应操作,与"不受权限配置约束"的领域语义直接冲突。ADR 0008 中"恒为当前代码的全量权限点"自本决策起读作"全量正向权限点"。

拒绝的方案:

- **独立的禁止字段**(如 `role.forbiddenPermissions`)——多一列就多一套校验/迁移/编辑器状态,而限制类权限点预期极少;沿用同一数组,复用全部既有管线。
- **正向表达**(`user.change_own_password`,不勾=禁止)——存量角色全部未勾,上线即全员被禁止改密;默认允许的能力只有用禁止式权限点表达,才能让存量角色行为保持不变。

影响:`hasPermission` 一族对权限点的"含有"一律当授予;对限制类权限点,含有意味着**禁止**——未来的执法守卫必须按此语义取反使用。本期只落基础(定义/管理员排除/角色编辑器),`user.forbid_change_own_password` 的实际执法随修改密码功能落地。
