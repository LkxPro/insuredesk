# 回调投递 = outbox 表 + 进程内轮询 worker（系统首个后台任务）

退费异常工单完结后须向平台投递 AES 加密回调，且合同规定平台应答 `data:false` 时工单系统须稍后重试——这是一个带重试义务的出向副作用，仓库既有教义「无后台任务、一切读时计算」无法承担「必须发出」的职责。决定：完结事务内落 `callback_deliveries` 投递行（载荷快照：endorNo/实退金额/补偿金/备注/操作人/工单号）；进程内轮询 worker 串行 tick 投递（纯函数 tick + 注入时钟，测试直接驱动 tick，不依赖假定时器）；pending-until-success——投递成功才落终态，崩溃/重启造成的重复投递由平台幂等吸收（at-least-once，合同已约定重复回调返回成功不重复处理）；退避 5m→30m→2h 循环，自首试 24h 转死信；传输失败（非 200/超时/非 JSON）与 9999 可重试，9998（解密/参数类）不重试；死信与 9998 均告警管理员，退费模块提供人工重新投递。

## Considered Options

- **独立 worker 进程**——prod 是单 api 容器，为一个回调增加部署单元不值。
- **引入队列基础设施**（bullmq/Redis 等）——为单一集成的低频回调新建基础设施，过度。
- **完结时同步直发**——完结可用性被平台可用性绑架（平台挂了客服无法完结工单）。
- **fire-and-forget**——合同的重试义务无人承担，闭环断裂。

## Consequences

仓库的后台任务先例由此开始；单实例部署假设记录在案，未来 api 水平扩容须先给投递加原子认领。完结不阻塞于回调成功（先完结、最终一致），工单退费模块展示投递状态供客服自查。
